# ADR-0001 — Every figure comes from the API, which reads Postgres; the browser engine survives only as a badged offline chunk

Status: Accepted · amended 2026-09-20 (see Amendment)
Date: 2026-09-03

## Context

At adoption `apps/web/src/lib/view.ts` imports `@dhan/core` and `@dhan/fixtures` and runs the
whole advisory engine in the browser over generated data, keeping the simulated clock and the
decision history in `localStorage`. That is fine for a demo and wrong for a bank: nothing a
customer sees is recorded anywhere, two devices can disagree, and the synthetic-data package ships
to every phone. The engineering rule in CONTRIBUTING is that browsers talk to the API and nothing
else. At the same time, reviewers will open the public link on hotel wifi, and a blank screen when
the API is unreachable would end the review before it started.

## Decision

`apps/web` renders `/api/v1/view`, `/record` and `/transactions` and holds only a bearer token.
The in-browser engine (`@dhan/core` + `@dhan/fixtures` + `buildView`) moves to
`apps/web/src/offline/`, lazy-loaded only when `/view` fails after two retries, shown with a
persistent "Offline — local simulation, nothing you do here is recorded" badge and decision
buttons disabled, behind `VITE_OFFLINE_FALLBACK`. The bank and GO Mobile+ build sets it false and
CI asserts the chunk is absent.

## Alternatives

- Drop the browser engine entirely and serve a cached last-good View. A first-time reviewer with
  the API down sees a blank app.
- Keep the engine in the main path as a fallback tier that recomputes silently. This violates the
  "every figure comes from the API" rule and produces two truths.

## Consequences

The rule is checkable in DevTools; the parity test guards the offline chunk against the API;
reviewers on hotel wifi always see a working, labelled product; the fixtures package stays out of
the production bundle.

## Amendment — 2026-09-20

`apps/web` has been deleted from the repository, by the repo owner's instruction, on the grounds
that `apps/mobile` is the product now. The badged offline chunk went with it: there is no
`apps/web/src/offline/`, no `VITE_OFFLINE_FALLBACK`, and no CI assertion that the chunk is absent
from a bank build, because there is no bundle left to assert over.

Read the title as two clauses joined by a semicolon, and only the second one is retired. The
first — **every figure comes from the API, which reads Postgres** — is not weakened by this; it is
strengthened. It was adopted as a rule with one deliberate, badged exception, and the whole of the
Decision above is the machinery of that exception: the lazy chunk, the flag, the persistent
"nothing you do here is recorded" badge, the disabled decision buttons, the parity test holding
the chunk to the API's arithmetic. With the chunk gone the rule is unconditional. There is exactly
one place a figure can come from, and the parity test is no longer the thing that keeps two
implementations of the engine agreeing, because there is only one.

What that costs is the thing the Context paid for. The first Alternative — *"Drop the browser
engine entirely and serve a cached last-good View"* — was rejected because *"a first-time reviewer
with the API down sees a blank app"*, and the tree now sits slightly worse than even that, which
should be recorded plainly rather than left to look like the Decision above still holds.
`apps/mobile` holds its View in memory and keeps it standing when a **refresh** fails
(`apps/mobile/src/state/snapshot.tsx:43-49`), so a reviewer already looking at a screen keeps
looking at it; there is no persisted cache, so a cold start with the API unreachable reaches
`state: 'error'` and the sentence *"Could not reach the bank."* (`:95-96`). The second Alternative,
the fallback tier that recomputes silently, was rejected on the "two truths" argument and stays
rejected — and with no second engine in any client it is now rejected by construction rather than
by discipline.

Consequences, as they stand today: the rule is still checkable — the mobile client holds a bearer
token and nothing else — and `@dhan/fixtures` reaches no client at all, which is a stronger
statement than the flag ever bought, since `apps/mobile` does not import it in any configuration.
It does import `@dhan/core`, and that is not the offline engine returning: it takes named helpers
and constants (`seriesKey`, `protectionShelf`, `netWorth`, `SMART_SAVE_FACTOR`) so a label on a
screen and the figure the API derived cannot drift apart. It never builds a View. The parity test
and the DevTools check named in the Consequences above describe a client that no longer exists.
