# ADR-0001 — Every figure comes from the API, which reads Postgres; the browser engine survives only as a badged offline chunk

Status: Accepted
Date: 2026-09-03

## Context

At adoption `apps/web/src/lib/view.ts` imports `@dhan/core` and `@dhan/fixtures` and runs the
whole advisory engine in the browser over generated data, keeping the simulated clock and the
decision history in `localStorage`. That is fine for a demo and wrong for a bank: nothing a
customer sees is recorded anywhere, two devices can disagree, and the synthetic-data package ships
to every phone. The engineering rule in CONTRIBUTING is that browsers talk to the API and nothing
else. At the same time, reviewers will open the public link on hotel wifi, and a blank screen when
the API is unreachable would end the review before it started.

## Decision

`apps/web` renders `/api/v1/view`, `/record` and `/transactions` and holds only a bearer token.
The in-browser engine (`@dhan/core` + `@dhan/fixtures` + `buildView`) moves to
`apps/web/src/offline/`, lazy-loaded only when `/view` fails after two retries, shown with a
persistent "Offline — local simulation, nothing you do here is recorded" badge and decision
buttons disabled, behind `VITE_OFFLINE_FALLBACK`. The bank and GO Mobile+ build sets it false and
CI asserts the chunk is absent.

## Alternatives

- Drop the browser engine entirely and serve a cached last-good View. A first-time reviewer with
  the API down sees a blank app.
- Keep the engine in the main path as a fallback tier that recomputes silently. This violates the
  "every figure comes from the API" rule and produces two truths.

## Consequences

The rule is checkable in DevTools; the parity test guards the offline chunk against the API;
reviewers on hotel wifi always see a working, labelled product; the fixtures package stays out of
the production bundle.
